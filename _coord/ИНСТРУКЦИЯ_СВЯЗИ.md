## 1. Зачем это нужно

В волте `R_vault` и его проектах (в первую очередь торговая система `R-trade` и литературный проект `R_tail.0.4`) одновременно или попеременно работают разные нейросети:
- **Gemini** (Antigravity IDE / CLI, локально)
- **Claude** (Claude Code локально / claude.ai облако; позывные «спредер», «R_tail»)
- **Kimi** (Kimi IDE / веб)

Чтобы модели не перетирали код друг друга, не дублировали исследования, знали актуальный контекст и могли передавать задачи по цепочке, создан единый протокол координации и **общий файл переписки: `_coord/CHAT.md`**.

## 3. Правила переписки в `_coord/CHAT.md`

`CHAT.md` — это единая хронологическая лента диалога нейросетей между собой и с Романом.

### Правило 1: Pull перед чтением и записью
Перед добавлением записи обязательно выполнить:
```bash
git pull --rebase --autostash origin main
```
Это гарантирует, что ты не затрёшь реплику, отправленную другой нейросетью минуту назад.

### Правило 2: Append-only (только дописывать в конец)
- Запрещено менять, перефразировать или удалять чужие сообщения.
- Каждая новая реплика добавляется **строго в конец файла**.

### Правило 2.1: Предотвращение и разрешение git-конфликтов
Почему Клод изначально создал папку `inbox/`? Потому что «один файл = одно сообщение» гарантирует отсутствие git-конфликтов при одновременных коммитах из облака (облачный Claude на claude.ai) и с локального ноутбука.

При работе с единым файлом `CHAT.md`:
1. **Штатный режим**: Роман переключается между нейронками по очереди. В этом случае конфликтов нет — достаточно сделать `git pull --rebase` перед записью.
2. **Если две нейронки написали одновременно**: при `git pull --rebase` может возникнуть конфликт слияния в конце `CHAT.md`.
   - **Правило разрешения**: сохранить **обе** реплики (согласно их времени `[ГГГГ-ММ-ДД ЧЧ:ММ]`), ничью реплику не удалять. Затем `git add _coord/CHAT.md` и `git rebase --continue`.
3. **Для фоновых / независимых параллельных задач**: если сессии работают автономно и не требуют единого диалогового треда, они могут использовать `_coord/inbox/`.

### Правило 3: Стандартный формат сообщения
Каждая реплика оформляется следующим блоком:

```markdown
---
### [ГГГГ-ММ-ДД ЧЧ:ММ] От: <Имя> | Кому: <Получатель или Всем>
**Тема / Задача**: <Кратко суть>  
**Статус**: [INFO / QUESTION / ACTION REQUIRED / DONE]  

<Основной текст сообщения: суть предложения, вопрос, результаты анализа, решение>

- **Затронутые файлы**: [ссылка на файл](file:///...)
- **Что требуется от коллеги / Романа**: <Конкретное действие или «ничего, к сведению»>
---
```

### Правило 4: Безопасность — абсолютный приоритет
1. **Никаких секретов**: репозиторий может быть публичным на GitHub. Запрещено писать в чат ключи API, токены, пароли, логины, номера карт и телефонов.
2. **Торговые правила**:
   - Bybit API — строго read-only. Никаких ордеров через код.
   - Правило Романа: **«Не фиксировать убытки»** (хеджирование, роллы, арбитраж, дельта-нейтральность).
   - Цифры — только проверенные из API/файлов, догадки помечать `догадка:`.

## 4. Чек-лист нейросети при старте и завершении сессии

### Старт сессии:
1. Выполнить `git pull --rebase origin main`.
2. Прочитать:
   - Корневой `CLAUDE.md` и `AGENTS.md`.
   - `_coord/README.md`.
   - **Последние сообщения в `_coord/CHAT.md`** (обратить внимание на вопросы или задачи, адресованные тебе).
   - При необходимости заглянуть в `_coord/status/` коллег.
3. Если есть открытый вопрос к тебе — дать ответ в `_coord/CHAT.md` (или выполнить задачу и отчитаться).

### Завершение сессии:
1. Записать итог работы в `_coord/CHAT.md` (что сделано, что протестировано, где возникли вопросы, кому передаётся эстафета).
2. Обновить свой статус в `_coord/status/<твой-позывной>.md`.
3. Закоммитить изменения явными путями (с префиксом проекта, например `[R-trade]`, `[R_tail]`, `[общее]`) и сделать push.
